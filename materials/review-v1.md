## 1. 総合評価
--------------------------------------------------------------------

結論：**構造修正＋順序変更が必要**（軽微修正では足りない）。

第1版は「全30組がコンパイル・実行できる」「15回の大枠（前半で新しいJava→後半で総合実習→最後に総復習）」という点では土台として使える。
ただし、教育目標（読める・予想できる・書ける・直せる・変更できる・機能追加を試せる）に対して、次の4つの構造的な問題がある。

### 問題1：基本文法をコードで一度も練習していない（最重要）
15回分・73ファイルの中に、次の構文が**1回も登場しない**。

- while / do-while / switch / break / continue
- && / || / !、% 、+= / -= などの複合代入
- 型変換（キャスト）、final（定数）、double
- 配列の `new 型[要素数]`、添字によるループ、`length`
- static 変数、オーバーロード、コマンドライン引数、instanceof

`else` の初出は第29回、通常の for 文の初出は第30回である。
learning-objectives.md で A（自力で書ける）に置いた LO03〜LO06（変数・演算子・if/switch・繰り返し・配列）を、後期のコードで練習する場面がほぼない。
「前期は学習済み・習得済みとは仮定しない。実践の中で繰り返し使って定着させる」という方針が、コード上で実現できていない。

### 問題2：exercise が「課題」になっていない
exercise の多くは、sample の値だけを変えたコピーである。そのため、レジメの演習の指示が
(a) すでに exercise のコードで完成している、または
(b) exercise に存在しないクラスやフィールドを前提にしている。
詳細は第2章と第6章に記載したが、15回中およそ12回で、演習の指示とコードが合っていない。
学生が「書く」量はほぼゼロで、自力記述や変更の機会が成立していない。

### 問題3：題材のコードが回ごとにリセットされ、積み上がらない
`Character` クラスは毎回作り直されており、前回の機能が消えている。

- 第17回：hp、damage、getHp がある
- 第18回：damage、getHp が消える
- 第19回：hp 自体が消える
- 第22回：hp が戻るが getHp はない
- 第23回：name だけになる
- 第26回：抽象クラスのバトルになる
- 第27回：通常クラスに戻り、Hero / Enemy が消える
- 第28・29回：attack と damage だけの最小クラスになる

その結果、次の問題が起きている。

- 第28〜29回の「既存プログラムへの機能追加」の土台が、第26回の統合版より貧弱である（ターンのループなし、パーティなし、Hero / Enemy なし）。
- 「前回のコードでは困る → 新しい機能で解決する」という流れ（必要になってから教える）が作れない。

### 問題4：レジメが template.md の粒度に達していない
template.md（Web教材の第16回）は約440行あり、手順、コード、実行結果、ヒント、発展が具体的に書かれている。
Java のレジメは各33〜65行で、次のものがない。

- sample のコード本文と実行結果
- Pleiades の操作手順
- 講義内容（解説）の節
- 演習の完成条件とヒント

講師の口頭説明に頼る量が多く、学生が自分で読み進められない。

### 評価のまとめ
| 観点 | 評価 |
|---|---|
| そのままでよい | 不可 |
| 軽微修正 | 不十分（問題1〜4はファイル単位の手直しでは解消しない） |
| 構造修正 | **必要**（継続するコードベース化、exercise のスターター化、基本文法の組み込み、レジメの書き直し） |
| 順序変更 | **必要**（配列より前にポリモフィズムで配列を使っている。OOP構造系が6回連続している。interface / package の位置） |

## 5. Bronze以外の実践Java（残す理由）
--------------------------------------------------------------------

| 内容 | 残す理由 | 推奨の扱い |
|---|---|---|
| ArrayList | 「仲間が増える、倒した敵が消える」はゲームの最も自然な要求で、配列の限界（サイズ固定）を体験した後に解決策として学べる。実務・教科書（第16章）でも最頻出 | 必須B。独立回（第24回）で扱い、統合バトルで使う |

## 7. 第19回・第21回の改善案
--------------------------------------------------------------------

### 7-1. 第19回（abstract class ＋ interface）
判断：**同じ90分で両方を導入するのは不適切。分離する。**
- 新しい概念が4つ（abstract class、抽象メソッド、interface、implements）あり、さらにinterface実装時のpublic制約が加わる。第18回（extends、super、override）の直後で、定着前に積み上げている。
- 実装クラスがHero1つだけなので、interfaceの必要性（継承と関係なく同じ能力を持たせたい）が示せず、「必要になってから教える」原則に反する。

提案：
| 要素 | 扱い | 回（推奨） | レベル |
|---|---|---|---|
| abstract class、抽象メソッド | 単独の主題にする。「Characterそのものをnewするのはおかしい」「attackを書き忘れた子クラスをコンパイラが止めてくれる」を体験させる | 第23回（ポリモフィズムの直後） | B/C |
| interface、implements | 後ろへ移す。統合バトルに「回復できる」能力を追加するとき、HeroにもEnemy（回復する敵）にも付けたい、という場面で導入する | 第28回 | C（読んで説明）＋一部B（既存interfaceを1クラスに実装） |
| interface実装時のpublic | interfaceの回で「エラーを読む」題材にする（publicを付け忘れたときのコンパイルエラー） | 第28回 | D |
| 具象・抽象・interfaceの比較 | 表で整理し、確認問題で判断させる | 第28回、第30回 | D |

削除はしない。抽象クラスはポリモフィズムの直後に置くと必要性が最も自然に出るため、順序を「ポリモフィズム→抽象クラス」に入れ替える（教科書は第11章→第12章の順だが、授業ではポリモフィズムを先に体験する方が動機付けしやすい）。

### 7-2. 第21回（package、import、static、Random）
判断：**4要素＋Pleiades操作は過負荷。既習・新規・利用のみに分けて分散させる。**

| 要素 | 分類 | 扱い | 回（推奨） | レベル |
|---|---|---|---|---|
| staticメソッド | 早めに「使う」 | メソッドの回でmainから呼ぶstaticメソッドとして書く（意味は後で説明） | 第18回 | B |
| import | 新規（軽い） | ArrayListを使うときに初めて必要になる | 第24回 | B |
| Random | 利用のみ | importの2例目。敵の行動に使う | 第25回 | B |
| package | 新規（主題） | Pleiadesでpackageを作り、Characterなどを移す。フォルダとpackage名の対応、java.langの自動import（Characterとの同名問題）を扱う | 第25回 | B/C |
| static変数 | 新規（小） | 「生成されたキャラクターの数」を数える。インスタンスごとの値との違いを予想させる | 第25回 | C |
| 標準API全般 | 紹介 | Math.max等を1つ例示し、APIドキュメントの見方に触れる | 第25回 | C |

これで第25回の新規要素は、package（主題）、static変数（小）、Random（利用）の3つになり、staticメソッドとimportは既習の状態で臨める。

### 10-2. 教材共通の修正ルール（第2版の基準）

- **Bronze確認**：各回の末尾に同じ形式のオリジナル問題を3問入れ、第30回で横断する。
